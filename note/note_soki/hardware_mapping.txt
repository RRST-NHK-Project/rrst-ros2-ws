#soki 実機ハードウェア 減速比・伝達機構メモ (2026-08-27作成)
関節角度の実機/sim校正(note/claude_task.txt参照)のための基礎データ。

## root_theta_joint (旋回)
CubeMars AK40-10 (Servo/MITモードで直接駆動、アクチュエータ内蔵クローズドループ)
+ 外部減速ギア追加あり。減速比 = 112/24 (= 14/3 ≒ 4.666667)
  root_theta_joint角度 = AK40-10側のエンコーダ角度 / (112/24)
  (AK40-10自体の内蔵ギア比は別途アクチュエータ仕様通り。ここでの112/24は
   さらに外側に付いている減速ギアの比。2026-08-27、13と5/7(96/7)から変更)

tip_theta_jointは root_theta_joint とは別方式: タイミングベルト+プーリで
モーター側20T・手先側28T(減速比 = 28/20 = 1.4 = 7/5)。
  tip_theta_joint角度 = アクチュエータ側エンコーダ角度 / 1.4 ( = * 5/7 )

**方針変更(2026-09-08、ユーザー報告)**: root_theta側のAK40-10が電源逆接続で
焼損した。無事だったtip_theta側のAK40-10をroot_thetaへ転用し(CubeMars駆動・
Set Origin方式は変わらず)、tip_theta側には新規にRoboMas M2006+C610(z/rと
同一device_id=21のバスに3台目、M3=motor index 2)を導入した。tip_thetaは
z/rのような差動ミックスではなく単独直接駆動(joint_deg = actuator_deg /
tip_theta_reduction、reduction値=1.4は変更無し)。原点センサが無いため、
電源投入前に機構原点(0deg)へ手で合わせておく前提とし、M2006内蔵ロータ
エンコーダの起動時リセット値(=0)をそのまま原点として使う(ホーミング処理は
無し。real_joint_bridge.yaml/real_joint_bridge_node.py/trajectory_follower_node.py
のtip_theta_offset_radは微調整用にのみ残す)。詳細はcommand_gui_node.py側の
「原点センサ・ホーミング配線設定」注記、および下記「ros2can CAN_ID・スロット
割当」「root_theta/tip_thetaの原点初期化」の各節も参照。

## z_joint / r_joint (motor1/motor2差動、M2006+C610)
**方針変更(2026-08-31、ユーザー判断)**: 位置の真値はC610/M2006内蔵ロータ
エンコーダのCAN帰還(ROBOMASのM{n} angle)を使う。以前は外付けAMTエンコーダ
(ENC1/ENC2、CAN_HOST配下ノードのローカルチャンネル)を真値としていたが、
ロボマス内蔵エンコーダに統一したため不使用になった(ENC1/ENC2自体の配線情報は
note/can_mapping.txt「外付けAMTエンコーダ」に不使用の注記付きで残してある)。
これにより「MIT位置フィードバックは内蔵エンコーダ、較正の真値は外付けENC」という
2系統だった構成が、内蔵エンコーダ1本に統一された。
ロボマス(M2006)モーター軸 → プーリ(ピッチ円直径22.92mm、確認済み) →
タイミングベルトで機構に接続。
  pulley_radius = 22.92 / 2 = 11.46mm (ピッチ円直径なのでこれを直径として半分にする)
  motor1_joint/motor2_joint(線形変位、m) = motor_angle[rad] * pulley_radius[m]
    motor_angle[rad] = M{n} angle帰還(0.1deg/LSB、cubemarsの帰還と同じ
    スケール。robomas.cpp参照) をradへ変換したもの
この線形変位に対して、既存の差動ミキシング(soki_sim/scripts/motor_mixer_node.py)が
そのまま適用される:
  z = k*(m1+m2), r = k*(m1-m2), k = 0.5
上下限の原点センサは合成後のz/r軸それぞれに付いている(motor1/motor2の
個別軸ではない、確認済み)。相対エンコーダのため毎起動ホーミング必須
(詳細はnote/claude_task.txt「実機とsimの関節角度校正」参照)。
実装: soki_sim/scripts/real_joint_bridge_node.py、homing_node.py両方とも
robomas_device_id(21)のserial_rx_*_unwrappedを購読してM{n} angleを読む方式に
書き換え済み(2026-08-31)。CAN_HOST(device_id=101)はz/r原点センサ
(SW1/SW2のリミットスイッチ)の読み取りにのみ、引き続きhoming_nodeが使う。

## root_theta/tip_thetaの原点初期化(θの「毎起動ホーミング」は不要な設計)
z/rと違い、CubeMars AK40-10は絶対値エンコーダなので機構の原点自体は
電源off/onを跨いで保持される。ただしros2canの/zero_channelはオフセットが
GUIプロセスのメモリ上限りで永続化されない(ros2canプロセスの再起動だけで
消える)ため、これに頼ると絶対値エンコーダの利点が活きない。

**方針変更(2026-08-27、ユーザー判断)**: root_thetaはソフトウェアオフセット
(root_theta_offset_rad)方式を廃止し、CubeMars AK40-10本体へ「Set Origin」CAN
コマンド(Servo(CAN)モードcontrol_mode_id=5、永久原点=フラッシュ保存)を直接
送信することで、実機エンコーダ自体の原点を較正する方式に変更した。
  実装:
  - ros2can/firmware/xiao-esp32-s3_can2io/src/cubemars.cpp:
    control_mode=3(CUBEMARS_MODE_SET_ORIGIN)を新設。target[m]スロットを
    origin_mode(0=一時原点/1=永久原点/2=デフォルト復元)として流用し、
    CUBEMARS_CMD_SET_ORIGIN(=5)でCANへ送信する。フラッシュ書き込みを伴う
    ため、mode=3が複数周期継続してもエッジ検出で1回だけ送信する。
    ※ control_mode_id=5がAK Series Module Product Manual V3.2.0 4.1節の
    実際の記載と一致するかは2026-08-27時点で未検証(RPM=3/POS=4の続き番号
    として採用)。実機投入前にR-Link/マニュアルで要確認。
  - soki_sim/scripts/trajectory_follower_node.py: /set_root_theta_origin
    (std_srvs/Trigger)サービスを新設。呼び出すとroot_theta_jointについて
    数周期だけ通常のMIT指令を止め、CUBEMARS_MODE_SET_ORIGIN+永久原点を送信する。
  - soki_sim/scripts/real_joint_bridge_node.py: root_theta_offset_rad
    (ソフトウェアオフセット補正)を削除。root_theta = raw_angle / reduction
    のみとなった(motor側の原点が真の機械原点と一致している前提)。
  較正手順(実機組み立て後に1回だけ): 関節を原点センサの位置(真の機械原点)へ
  物理的に合わせ、/set_root_theta_originを呼び出す。以後はros2can・
  real_joint_bridge_nodeの再起動、電源off/onを跨いでも再較正不要
  (エンコーダ自体がズレない限り。フラッシュ保存のためros2can側の
  プロセス再起動にも依存しない)。

tip_thetaは2026-09-08方針変更でCubeMars(絶対値エンコーダ)からROBOMAS M2006
(相対エンコーダ)へ移行したため、root_thetaのSet Origin方式・旧来のyaml
オフセット較正方式のどちらとも異なる第三の方式になった: 原点センサが無いため、
電源投入前に機構原点(0deg)へ手で合わせておき、M2006内蔵ロータエンコーダの
起動時リセット値(=0)をそのまま原点として扱う(ホーミング処理は無し)。
real_joint_bridge.yaml/real_joint_bridge_node.py/trajectory_follower_node.pyの
tip_theta_offset_radパラメータは残しているが、通常は0のままでよく、実機の
微小な取付誤差を補正したい場合にのみ使う(root_thetaのSet Originのような
「一度較正すれば恒久的に有効」という永続化ではない点に注意。電源off/onの
たびに手動ゼロ合わせをやり直す運用が前提)。
z_joint/r_jointは元々毎起動homing_nodeが/zero_channelを呼ぶ設計なので、
こちらはros2can側オフセットが非永続でも問題ない(むしろ意図通り)。

## root_theta/tip_thetaはMITモードの都合上そもそも「continuous」ではない
## (2026-08-27、AK Seriesマニュアル確認により判明。対応方針決定済み)
claude.txt/soki_sim.urdf.xacroではroot_theta_joint(旋回)/tip_theta_joint
(手先回転)を無制限回転可能なcontinuous関節として扱っているが、実際には
MITモードのプロトコル仕様そのものにより可動域が制限される。

CubeMars AK SeriesのMITモード位置指令(pos_des)は、ros2can側の実装
(firmware/xiao-esp32-s3_can2io/src/config.hpp、CUBEMARS_MIT_P_MIN_RAD/
MAX_RAD = ±12.5f)、およびマニュアル記載のParameter range表(AK40-10含む
全モデル共通)の両方で ±12.5rad(=±716.2°)固定と確認済み。これはMIT
Cheetah系アクチュエータ共通のプロトコル制約(16bit固定小数点で8byteに
position/velocity/Kp/Kd/torqueを詰め込む都合)で、ros2can側の設定ミスでは
ない。範囲外を指令してもcubemars.cppのfloatToUint()内でクランプされる
(x = std::min(std::max(x, x_min), x_max))。
外部減速比を通すと指令できる範囲は
  root_theta_joint: ±716.2°/4.6667(=112/24) ≒ ±153.5°
  tip_theta_joint : ±716.2°/1.4    ≒ ±511.6°(約1.4回転)
と、いずれも1回転に満たない(root_theta)か1回転強(tip_theta)程度しかない。

CubeMarsのServo(CAN)帰還フレームのposition値(int16・0.1deg/LSB)も
AK Series Module Driver Manual V1.0.18 5.2.1節により有効範囲が
-32000~32000(=±3200°、AK40-10出力軸換算で±8.89回転)止まりと判明して
いたが、上記の指令側の制約(±52.2°/±511.6°)のほうがずっと狭いため、
実際の可動域では帰還側の境界には到達しない(指令できる範囲の方が先に
尽きるため)。よってposition帰還のクランプ/ラップ挙動そのものは実運用上
問題にならない。

**方針決定(2026-08-27、ユーザー判断)**: 上記の通りMITモードのままでは
真の意味でのcontinuous回転は不可能。デッドレコニング(速度積算による
連続絶対位置推定)やServo(CAN)モードへの制御方式変更は行わず、
「一旦制限つきでよい、MITモードの可動域(root_theta:±153.5°、
tip_theta:±511.6°)の中だけで動作すればよい」という前提で運用する。
ros2can/real_joint_bridge_node.py側のコード変更は不要(既存のposition
帰還ベースの実装のまま)。
  将来もし真のcontinuous回転が必要になった場合の選択肢(未着手):
  (a) Servo(CAN) Velocity Loop Mode(mode 3、指令範囲の制約なし)+
      ホスト側(real_joint_bridge_node.py等)での位置制御ループを新規実装
  (b) Servo(CAN) Position-Velocity Loop Mode(mode 6、指令範囲±36000°=
      ±100回転)へ切替。MIT特有のKp/Kdによる柔らかい制御は失う。
  いずれもMITモードからServo(CAN)モードへの制御方式変更が必要で、
  現状は選択していない。

**2026-09-08追記**: 上記のtip_theta可動域(±511.6°)はCubeMars駆動時代の
制約(CUBEMARS_MIT_P_MIN/MAX_RAD=±12.5rad)に基づくもの。tip_thetaが
ROBOMAS(M2006、M3)へ移行した後は、robomas.cpp側のMIT位置指令に
CubeMarsのような明示的なmin/maxクランプが無く、int16(1deg/LSB、
ROBOMAS_MIT_POSITION_LSB_DEG)の範囲=アクチュエータ軸±32767°(±91回転、
tip_theta_reduction=1.4を通すと関節側±23383°=約65回転相当)まで指令できる
ため、実質的にCubeMars時代より大幅に広い(このAK Series特有のMIT範囲制約
自体がtip_thetaには適用されなくなった)。ただし依然としてcontinuous関節
ではなく有限範囲である点は変わらないため、上記(a)(b)のようなServo(CAN)
モードへの変更を行わない限り、ソフトウェア側(trajectory_follower_node.py
のtarget_callback等)で想定外の大回転指令が来ないよう運用上の注意は必要。

## z_joint/r_jointのホーミング (homing_node、2026-08-27実装)
z=k(m1+m2)/r=k(m1-m2)という合成後の量は、ros2canの/zero_channel(ENC単体を
ゼロ化するだけ)では正しく較正できないため、root_theta/tip_thetaと同様に
real_joint_bridge_node側のランタイムパラメータ(z_offset_m/r_offset_m、
ただしこちらはyaml初期値ではなく毎起動homing_nodeが計算してSetParameters
で書き込む値)で補正する方式にした。
  手順(2026-09-05よりz軸/r軸は別サービスに分離、任意の順序・タイミングで
  独立に実行できる。ただし差動機構のためどちらの軸でもmotor1/motor2両方が
  回転する):
    start_homing_z: motor1/motor2を同方向に駆動しz軸原点センサ検出→z_offset_m算出
    start_homing_r: motor1/motor2を差動方向に駆動しr軸原点センサ検出→r_offset_m算出
    (いずれも検出したoffsetをreal_joint_bridge_nodeへSetParametersで反映)
  実装: soki_sim/scripts/homing_node.py。安全のため自動起動はせず、
  start_homing_z/start_homing_r/stop_homing(std_srvs/Trigger)サービスで
  明示的に起動・中断する。パラメータはreal_joint_bridge.yamlのhoming_node以下。

  skip_homing(std_srvs/Trigger、2026-08-29追加): 原点センサ配線・検出値が
  未検証(下記「未確認事項」参照)なうちの代替手段。motor1/motor2を一切駆動せず、
  呼び出し時点のエンコーダ値をそのままz_ref_value_m/r_ref_value_mの位置と
  みなしてoffsetを即座に反映する(z/r両方まとめて、軸ごとの分離はない)。
  呼び出し前に機体を(joy等で手動操作して)原点センサ位置相当へ物理的に
  合わせておく必要がある点はstart_homing_z/start_homing_rの実際の較正結果と
  変わらない(センサでの自動検出をスキップするだけ)。

## z_joint/r_jointの実機出力(RoboMas MITモード) (2026-08-29追加)
ros2canのMODE_ROBOMASにMITモード(位置PD制御、firmware/xiao-esp32-s3_can2io/src/
robomas.cpp)が実装されたことを受け、root_theta/tip_theta(CubeMars MIT)と対称的に
z_joint/r_jointもtrajectory_follower_nodeからMIT指令を送れるようにした
(robomas_device_id等のパラメータで有効化。未設定時は従来通り実機出力無効)。

  実装: soki_sim/scripts/trajectory_follower_node.py
  - z/rは引き続きjoint単位で台形プロファイルし、送信直前にmotor_mixer_node.pyと
    同じ式(m1=(z+r)/(2*mix_k), m2=(z-r)/(2*mix_k))でmotor1/motor2側
    (アクチュエータ軸、プーリ半径換算)へ変換してから送信する。
  - スケールはcubemarsと異なるので注意: 指令(target)は1deg/LSB(cubemarsの
    0.1deg/LSBより粗い。範囲確保のため、robomas.cppのコメント参照)、帰還(angle)は
    0.1deg/LSB(cubemarsと同じ)。mit_kp=0.001(A/deg)/LSB、mit_kd=0.0001(A/rpm)/LSB、
    mit_current_ff=0.001A/LSB(config.hppのROBOMAS_MIT_*と一致させること)。
  - 位置フィードバック基準はロボマス内蔵ロータエンコーダ(root_theta/tip_thetaと
    同じ設計判断)。2026-08-31の方針変更でreal_joint_bridge_node/homing_node側の
    z/r真値も同じロボマス内蔵エンコーダに統一されたため、以前あった「MIT側は
    内蔵エンコーダ、較正側は外付けENC1/ENC2」という基準のズレ(バックラッシュ差分)
    は解消された。

**2026-09-08追記**: 同じdevice_id=21のM3(motor index=2)にtip_theta_jointも
同居させた(root_theta側AK40-10焼損に伴う駆動系変更、上記「root_theta_joint
(旋回)」節の方針変更参照)。z/rのようなmotor1/motor2の差動ミックスではなく、
tip_theta_joint単独の直接駆動(joint_deg = actuator_deg / tip_theta_reduction)。
ゲインはz/rの共有スカラー(robomas_kp/kd/current_ff)とは別に
robomas_tip_theta_kp/kd/current_ffを持つ(動特性が異なるため)。

**homing_nodeとの排他制御**: homing_nodeは起動時ホーミング中、同じ
robomas_device_idへ独立に速度指令をpublishするため、trajectory_follower_nodeの
MIT指令と衝突する。これを避けるため、trajectory_follower_nodeに
pause_robomas_output/resume_robomas_output(std_srvs/Trigger)を新設し、
homing_nodeがstart_homing_z/start_homing_r時にpause、stop_homing・各軸の
完了・タイムアウト失敗時にresumeを呼ぶ「一時停止パターン」(root_theta
origin設定の_origin_pending_と同種)で解決した。

**offsetの二重管理**: z_offset_m/r_offset_m(homing_nodeが算出する原点補正値)は
これまでreal_joint_bridge_node(sim表示用)のみに反映していたが、
trajectory_follower_node(実機MIT指令用)も独自にz/rの内部状態を持つため、
robomas_z_offset_m/robomas_r_offset_mという別パラメータ名でこちらにも
SetParametersするようhoming_node._apply_offsets()を拡張した。値・符号規約
(z = mix_k*(m1+m2) + offset)はreal_joint_bridge_nodeと揃えてある。

## mixed_joint_statesの真値ソース(2026-09-07方針変更)
実機テスト用launch(real_root_theta_test/real_axes_test/real_z_r_test/
real_all_axes_test.launch.py)では、trajectory_follower_nodeの内部軌道(pos_、
MIT指令生成用の理想値、実機の追従が遅れても即座には反映されない)と
real_joint_bridge_nodeの実測値(CAN帰還ベース)が、どちらも同じ
mixed_joint_statesトピックへ別々にpublishしており、joint_state_publisher/GUI/
RVizの表示がどちらが後に届いたか次第でブレる(simが実機より先行して見える)
問題があった。

**方針(ユーザー判断)**: simは実機が無い時のデバッグ用途であり、実機接続時は
simが実機の実測値に追従して表示すべき(逆に実機がsimの理想軌道に追従させられる
ように見えるのはおかしい)。そのため:
  - 上記4つのlaunchでtrajectory_follower_nodeのoutput_topicを
    'trajectory_target_joint_states'に分離し、mixed_joint_states(joint_state_
    publisherのsource、command_gui_node/joy_teleop_nodeが現在値として購読する
    トピック)にはpublishしないようにした。MIT指令自体はこれまで通りpos_を
    元に生成する(この変更の影響を受けない)。
  - real_joint_bridge_node.pyは、以前はCubeMars/ROBOMAS両方の帰還が揃うまで

## ロボマスCAN帰還の途絶検出 (2026-09-08、ユーザー報告の不具合対応)
**症状**: マイコン(ros2can xiao-esp32-s3_can2io、MODE_ROBOMAS)の電源は入れた
まま、C610/M2006側(モータ駆動)の電源だけを落として入れ直すと、電源投入の
瞬間にロボマスが勝手に動き出す。

**原因**: robomas.cppのreceiveFeedback()は、C610からのCAN帰還フレームが実際に
届いたときだけangle[]/vel[]/current_a[]を更新する作りだった。C610側の電源を
落とすと帰還フレーム自体が来なくなるが、マイコン自身は動き続けるため、
angle[]等は電源断直前の値で凍結されたまま、robomasTask()は毎周期(200Hz)
その凍結値を「現在値」としてMIT位置PD制御の誤差計算(pos_error = target -
angle[i])に使い続け、かつTx_16Data経由でホストへも凍結値をそのまま送信し
続けていた(ホスト側はメッセージ自体は正常な頻度で届くため途絶に気付けない)。
C610の電源が復帰すると、その瞬間の実際のロータ角度(1回転内のraw値)と、
凍結されたままのangle[]・ホストが送り続けている現在の目標値との間に大きな
差分が生じ、MIT PD制御がその差分を電流指令に変換してモータが唐突に動き出す。
さらに、周回検出(rotation_count、diffベース)が電源断中の物理的なズレを
「1周した」と誤検出し、angle[]をさらに狂わせる場合もある。

**対策(実装済み、robomas.cpp/config.hpp)**: モータごとにCAN帰還の最終受信
時刻を記録し、ROBOMAS_FEEDBACK_STALE_MS(既定100ms)以上帰還が無ければ
「途絶」とみなして電流指令を0に固定する(MIT/速度どちらのモードでも計算自体を
スキップ)。途絶から復帰した最初のフレームでは周回カウントをその場でリセット
(diffによる周回誤検出を防ぐ)し、復帰後ROBOMAS_RESYNC_HOLD_MS(既定200ms)は
引き続き電流指令を0に固定してangle[]の飛びがそのままモータへ出力されるのを
防ぐ。z/r側は元々毎起動homing_nodeでの再ホーミングが前提の設計なので、この
対策を入れても「電源復帰後は再ホーミングが必要」という運用自体は変わらない
(このケースはあくまで復帰の瞬間の唐突な動き出しを防ぐための安全対策)。
**要実機確認**: ROBOMAS_FEEDBACK_STALE_MS/ROBOMAS_RESYNC_HOLD_MSの値は暫定
(通常のCAN帰還間隔・電源off/onの時間スケールから逆算した値で、実機での
挙動未検証)。ファームウェアの再ビルド・書き込みが必要。

## homing_nodeのpause_robomas_output競合 (2026-09-08、ユーザー報告の不具合対応)
**症状**: z軸ホーミングでリミットスイッチに当たった瞬間に暴走する。ただし
毎回ではなく、時々しか起きない。

**原因**: homing_node._start_homing_axis()が、trajectory_follower_nodeの
pause_robomas_output(std_srvs/Trigger)を呼ぶのと同時に(応答を待たずに)
state_をHOMING_Z/HOMING_Rへ変えていた。次のcontrol_period_sec(既定50ms)後の
_on_tickはstate_だけを見てmotor1/motor2への速度指令送信を始めるため、
pause_robomas_outputの応答(trajectory_follower_node側でrobomas_paused_=True
になるタイミング)がそれより遅れて届くと、trajectory_follower_nodeがホーミング
開始前の位置を保持しようとするMIT位置指令と、homing_nodeの速度指令が同じ
serial_tx_{robomas_device_id}へ競合して送られる期間ができる。この間実機は
「元の位置を維持しようとするMIT指令」と「原点センサへ向かう速度指令」の
綱引き状態になり、原点センサ到達までに蓄積したMIT側の位置誤差が、どちらの
指令がESP32側の周期(200Hz)により遅く届くかという非決定的なタイミングに
応じて電流指令に反映される。pauseが実際に効くタイミング(ROS2のサービス
呼び出し・実行順序)に依存するレースコンディションのため、再現したりしな
かったりする。

**対策(実装済み、homing_node.py)**: pause_robomas_outputの応答が届く(または
サービス未提供と判明する)まではSTATE_PAUSING_Z/STATE_PAUSING_R状態に留まり、
_on_tickはこの間モータに一切指令を送らない。応答確認後に初めてSTATE_HOMING_Z/
STATE_HOMING_Rへ遷移してモータを動かし始める(ホーミング完了時にoffset適用を
待ってからresume_robomas_outputを呼ぶ、という以前の修正と対称の構造。z_offset_m
反映後のジャンプ対策と合わせて、「pause確認 → ホーミング駆動 → offset確認 →
resume」の順序をコード上で保証するようにした)。

**追加報告(2026-09-08、同日)**: 上記の順序保証だけでは直らず、依然として
ホーミング終了直後に目標値へ向かって動く(暴走のように見える)症状が残って
いた。ユーザー要望: 「ホーミング終了後に目標値に向かっているならやめて
ほしい。その位置で停止してもらって構わない」。

**根本原因**: trajectory_follower_node._on_robomas_feedback()は、
robomas_paused_中(=ホーミング中)は帰還のたびにpos_/target_をその場の実位置へ
追従させ続けるが、robomas_paused_がFalseに戻った(resume_robomas_output後)
瞬間からこの追従を止める(has_target_かつnot paused、で即return)。一方
homing_nodeがhoming完了時に送るrobomas_z_offset_m/r_offset_mのSetParameters
は、_apply_offsetの完了を待ってからresume_robomas_outputを呼ぶよう順序は
保証していても、「trajectory_follower_node側でoffsetパラメータの値が実際に
更新されてから、_on_robomas_feedbackが少なくとも1回はその新しいoffsetで
pos_/target_を再計算する」ことまでは保証していなかった。offset更新とresume
の2つのサービス要求はtrajectory_follower_node自身のexecutor上で処理される
ため、その間に_on_robomas_feedbackの呼び出しが挟まるかどうかはトピック到着と
executorのスケジューリング順序次第の非決定的な事象で、挟まらなかった場合は
pos_/target_が古いoffset基準のまま凍結され、resume後のMIT指令がその古い値
(=現在位置から見て新旧offsetの差分だけ離れた「目標」)へ向けて動いてしまう。

**対策(実装済み、trajectory_follower_node.py)**: _on_robomas_feedback()で
毎回(has_target_/robomas_paused_の状態に関わらず)最新のm1/m2を
self._last_robomas_m1_m2_へキャッシュしておき、_on_set_parameters()の
robomas_z_offset_m/robomas_r_offset_m変更ハンドラの中で、そのキャッシュ済み
m1/m2と新しいoffset値を使って同期的にpos_/target_/vel_を再計算・確定する
(z/rは差動ミックスなので、片方のoffsetだけが変わってももう片方も一緒に
再計算する)。これによりoffsetパラメータが変わった、まさにそのコールバックの
中でpos_==target_(その場で静止)が確定するため、_on_robomas_feedbackの次回
呼び出しタイミングやexecutorのスケジューリング順序に一切依存しなくなった。

## homing_nodeの原点センサ検出遅延 (2026-09-08、ユーザー報告の不具合対応)
**症状**: R軸の原点取りで、原点センサが反応していないような挙動(そのまま
突っ込む)をする。ただし毎回ではなく、しっかり止まることもある。

**原因**: 原点センサの検出は従来homing_node._on_tick()(control_period_sec
既定50msのタイマー)でのみポーリングしていた。IO_SW_Input()(ros2can
firmware pin_ctrl_task.cpp)はSWの生値をデバウンス無しでそのまま送っており、
homing_node._switch_triggered()もその時点の値をそのまま見るだけの単純な
レベル判定(エッジ検出・ラッチ無し)だった。センサが実際に検出されてから
_on_tickが停止指令を送るまでには、CAN/シリアル中継の遅延に加え最大
control_period_secぶんのポーリング遅延が上乗せされる。原点センサの検出範囲
(停止指令が効くまでに機構が進める余裕)がこの合計遅延より狭いと、センサの
検出範囲を通り過ぎてから停止指令が届くことになり「センサ無反応で突っ込む」
ように見える。この遅延量はCAN/シリアル中継やexecutorのスケジューリングに
依存する非決定的な量のため、状況によって間に合ったり間に合わなかったりする
(再現したりしなかったりする)。

**対策(実装済み、homing_node.py)**: 原点センサのチェックロジックを
_check_homing_switch()として切り出し、_on_tick(タイムアウト監視用のポーリング、
保険として引き続き呼ぶ)に加えて_on_can_host(CAN_HOSTの帰還を受信した
まさにそのコールバック)からも即座に呼ぶようにした。これによりポーリング周期
(最大50ms)ぶんの遅延が無くなり、CAN/シリアル中継の遅延だけが残る(こちらは
ハードウェア/通信経路側の遅延なのでソフトウェア側では詰め切れない)。
**要実機確認**: この対策後もまだ発生する場合は、原点センサの検出範囲(スイッチの
機構的な動作ストローク)自体が狭すぎるか、homing_velocity_rpm(既定30rpm)が
残った遅延に対して速すぎる可能性がある。後者はhoming_velocity_rpmを下げることで
軽減できる(real_joint_bridge.yamlのhoming_node節)。
